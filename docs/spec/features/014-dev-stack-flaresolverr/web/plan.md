# PLAN: Development Stack Contract and FlareSolverr — `web` (`web/plan.md`)

## Scope

One change, in one component: when a release search fails, the search dialog says so instead of
rendering an empty result table.

Today `SearchTorrent.tsx`'s `handleSearch` wraps the call in a `try/catch` whose entire handler is
`console.error({ error, query }, "Error al buscar torrents")`. The loading spinner stops, `results`
stays at its previous value (an empty array on a first search), and the user sees the same screen
they would see if the title genuinely had no releases. The error already reaches this point — the
`api` will raise it after `../api/plan.md`, and `searchTorrentsAction` already rethrows it — so this
slice is purely about rendering what is already in hand.

It is explicitly **not** doing: changing `services/web/src/actions/indexer.ts` (it already handles
the error correctly and needs no edit), changing `services/web/src/types/indexer.ts` (no shape
changes), touching the add-torrent path, or fixing any of the 4 pre-existing files that fail
`bin/npm web run build` — those are unrelated debt and widening this slice to include them would make
the diff unreviewable.

Writes are confined to `services/web/` and this directory. Anything else is a stop-and-report (see
`.claude/agents/web.md`).

## Existing code to reuse

- `SearchTorrent.tsx`'s own `addError` state and the JSX that renders it. The component **already
  has** an error surface, built for the add-torrent path — reuse that presentation rather than
  introducing a second style of error display in the same dialog. Whether that means widening
  `addError` into one shared error state or adding a sibling `searchError` beside it is an
  implementation call; what matters is that both errors look the same to the user.
- `services/web/src/actions/indexer.ts` — `searchTorrentsAction` already calls
  `redirectIfUnauthenticated(errors)` and then `throw new Error(errors[0]?.message || 'Error al
  buscar releases')`. It is correct as written: the thrown message is the `api`'s Spanish copy, which
  is what must reach the screen. **Do not edit this file.**
- `CONFLICT_MESSAGE` at the top of `SearchTorrent.tsx` — the existing precedent for how this
  component matches on a server message. Not needed here (the search error is displayed, not
  branched on), but it is the local convention if any matching turns out to be necessary.

## Steps

1. Add error state for the search path, alongside the existing `addError`.
2. In `handleSearch`, replace the `console.error`-only `catch` with one that stores the thrown
   `Error`'s `message`. Keep the `finally` that clears `isLoading`. Clear the error at the start of
   each new search so a retry does not show a stale message.
3. Also clear `results` when a search fails, so the dialog cannot show the previous query's releases
   next to an error about the current one.
4. Render the message in the dialog, matching the existing `addError` presentation.
5. Keep the `console.error` if it is useful for debugging — it is not the problem. Silently
   *stopping there* was.

## Contract obligations

From `../spec.md` § GraphQL Contract Delta, this slice is the consumer side of one error condition on
the existing `searchTorrents` query. There is **no schema change**: no new field is queried, and
`SEARCH_TORRENTS_QUERY` in `actions/indexer.ts` is untouched.

The two messages arrive from `api` and are rendered **verbatim** — they are already Spanish, already
user-facing copy, and this slice must not rewrite, prefix or translate them:

- `No se pudo consultar el indexer (HTTP <status>)`
- `No se pudo consultar el indexer`

The generic `'Error al buscar releases'` in `searchTorrentsAction` stays as the fallback for a
GraphQL response with no message. And the case that must **not** show an error: a successful search
with no matches still returns `[]`, and an empty list keeps meaning "nothing found". Rendering an
error there would undo the distinction REQ-15 exists to restore.

This slice cannot be verified until `../api/plan.md` step 4 lands — until the `api` raises, no search
produces the error to render. Write it in parallel, verify it after.

## Tests

**No test file.** `web` has no test harness — no runner, no `*.spec.tsx` anywhere in
`services/web/src`, and this feature is not the place to introduce one. The failure this slice fixes
is also not silent once the `api` change is in: the error is thrown and reaches the component, so the
only question is whether it is painted, which is exactly what AC-9 checks by looking at the screen.

The unit that genuinely could fail silently in this chain is the `api` client, and that is where the
one new test in this feature lives (`../api/plan.md` § Tests).
