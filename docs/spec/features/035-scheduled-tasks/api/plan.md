# PLAN: Scheduled Tasks — `api` (`api/plan.md`)

Read `../spec.md` and `../plan.md` first. The GraphQL delta there is read-only.

## Scope

This slice owns everything except the screen: the Prisma model and migration, the eight seeded
settings, the new `'cron'` setting kind and its validation, the `src/scheduler/` module (registry,
service, resolver, entities, four stub handlers), the three new error keys and their English
messages, and the re-arm hook on `updateSettings`.

It does **not** write any task logic — the four handlers return `{ itemsProcessed: 0 }` and touch
nothing. It does not touch `services/web/`, and it does not touch `src/queue/` or `worker`: a
scheduled task runs in-process here.

Writes are confined to `services/api/` and this directory.

## Existing code to reuse

- `src/settings/settings.catalog.ts` + `settings.service.ts::updateMany` — the `'int'` and `'enum'`
  branches are the exact shape the `'cron'` branch takes. Validate through `cron`'s `CronTime`
  (pulled in by `@nestjs/schedule`), throw `i18nError.badRequest(ERROR_KEYS.SETTING_EXPECTED_CRON,
  { key })`. Do not add a second validation entry point.
- `src/settings/settings.resolver.ts` — the "resolver fires the side effect after the write is
  confirmed" pattern (`qbittorrentClient.setSavePath`, `mediaServerIndex.rebuild`), including the
  `before`/`after` map comparison so an absent key never reads as "changed". The re-arm hook is a
  third block in the same method, same shape.
- `src/i18n/i18n-error.ts` — every throw goes through `i18nError.{notFound,conflict,badRequest}`.
  Never `new NotFoundException` directly.
- `src/ffprobe-logs/ffprobe-logs.resolver.ts` — the **per-method** `@UseGuards(AdminGuard)` form.
  Use this, not `UsersResolver`'s class-level form.
- `src/preferences/entities/torrent-group-scope.enum.ts` — the `registerEnumType` idiom for
  `ScheduledTaskOutcome`.
- `src/media-server/media-server-index.service.ts` — the precedent for a service that owns
  long-running background state and exposes a status object plus a manual trigger.
- `src/prisma/prisma.service.ts` — the only database access path.

## Steps

1. `prisma/schema.prisma`: add the enum and model. Generate the migration with
   `bin/npm api run prisma:migrate`. Both must appear in the diff (Article III).
2. `prisma/seeds/settings.ts`: append the eight rows with the defaults from `../spec.md`
   § Data Model Changes.
3. `package.json`: add `@nestjs/schedule`; install through `bin/npm api install`.
4. `src/scheduler/scheduler.registry.ts`: export a frozen array of four definitions —
   `{ id, defaultCron, handler }` — and a lookup by id. The `_enabled` / `_cron` settings keys are
   *derived* from the id (`schedule_<id>_enabled`), not written out four more times.
5. `src/scheduler/tasks/`: four stub handlers, each an injectable with one method returning
   `{ itemsProcessed: 0 }`. No TMDB, no indexer, no Prisma.
6. `src/scheduler/scheduler.service.ts`:
   - `onModuleInit`: close any run left `RUNNING` as `FAILED` (NFR-5), then arm from settings.
   - `arm()`: read `SettingsService.getMap()`, and for every registry entry that is enabled with a
     valid cron, register a `CronJob` in `SchedulerRegistry` under the task id; disarm anything no
     longer enabled. Called on boot and from the resolver hook. A malformed or missing value logs
     and leaves that task disarmed — never throws (NFR-2).
   - `runTask(id, trigger)`: the single execution path for both a cron tick and a manual call.
     Refuses if that id is already running (`SCHEDULE_TASK_ALREADY_RUNNING` for a manual call; a
     tick records a `SKIPPED` run instead of throwing, REQ-5). Writes the `RUNNING` row, invokes
     the handler inside try/catch, closes the row as `SUCCESS`/`FAILED` with `itemsProcessed` or
     the error message, then prunes. **Never rethrows into the cron callback.**
   - `list()`: one row per registry entry, joined to its latest run and to `CronJob.nextDate()`.
   - `prune(taskId)`: keep the most recent N runs (N a module constant), delete the rest.
7. `src/scheduler/entities/`: the three types, matching `../spec.md` field for field.
8. `src/scheduler/scheduler.resolver.ts`: the two operations, `@UseGuards(AdminGuard)` per method.
   `runScheduledTask` throws `SCHEDULE_TASK_NOT_FOUND` for an unregistered id and returns the same
   `ScheduledTask` shape `list()` produces.
9. `src/settings/`: the `'cron'` kind, its validation branch, the eight catalog entries, and the
   re-arm block in the resolver.
10. `src/i18n/`: the three keys and their English messages.
11. `src/app.module.ts`: import `SchedulerModule`.

## Contract obligations

Expose exactly `../spec.md` § GraphQL Contract Delta — `Query.scheduledTasks`,
`Mutation.runScheduledTask(id)`, and the `ScheduledTask` / `ScheduledTaskRun` /
`ScheduledTaskOutcome` types. The four error conditions must throw the keys in that table and no
others; `web` matches on `error.schedule.task_already_running` to re-render a row rather than show
a toast, so a differently-keyed conflict silently degrades that behaviour.

`src/schema.gql` regenerates on boot — never hand-edit it (Article IV).

## Tests

`src/scheduler/scheduler.service.spec.ts` — one file, opening with the Article IX header naming
the failure it defends against: **a scheduler that stops running with no error anywhere.** The four
units owed a test are exactly the silent ones from `../plan.md` § Risks:

- A run left `RUNNING` by a crash is closed on boot; without it, REQ-5's guard locks that task out
  permanently and nothing logs it.
- A handler that throws is recorded `FAILED` and the rejection never escapes `runTask` — an escaped
  rejection in a timer takes the process down.
- A concurrent invocation does not produce a second run row.
- Re-arming after a settings change replaces the armed job rather than adding a second one — two
  armed jobs for one task means every occurrence runs twice, which produces no error at all.

`scheduler.resolver.spec.ts` is **not** owed: the guard placement here is the ordinary per-method
form with no service principal to accommodate, so `ffprobe-logs.resolver.spec.ts`'s reason for
asserting metadata does not apply. The stub handlers are not owed tests — they do nothing, and the
test would only assert the stub, not the future behaviour.

Extend `src/settings/settings.service.spec.ts` with the `'cron'` rejection: an invalid expression
must leave the stored value untouched (AC-6), which is the same class of failure the existing
`'int'`/`'enum'` cases cover.
