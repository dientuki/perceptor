# PLAN: Download Status and Torrent Tags — `api` (`api/plan.md`)

Read `../spec.md` and `../plan.md` first. The GraphQL delta and the torrent-client interface delta
in `../spec.md` are **read-only** — if either is wrong, stop and report (Constitution, Article VIII).

## Scope

This slice owns everything except the screen: the Prisma migration that inverts
`Movie` ↔ `MediaSource`, the qBittorrent client methods, the tagging on every acquisition path, the
new `downloads/` read and control surface, the race arbiter in `torrentCompleted`, and the loser
sweep inside `downloadRemove`. It also narrows seven conflict guards so that only a **`COMPLETED`**
target refuses — `force`, the `…_ALREADY_COMPLETED` keys and everything else
`027-replace-completed-media` owns stay exactly as they are (`../spec.md` REQ-7).

It is **not** building the panel, the refresh control, the confirmation dialog or any Spanish UI
copy beyond exception messages — `web` owns those. It is **not** touching `services/worker`: the
worker's call sites and payloads are unchanged, and `encode.job.ts:146`'s rethrow already makes
cleanup unreachable on a failed encode, which is what REQ-16 asks for. A change that appears to
require editing `services/worker` is a contract error — stop and report.

Writes are confined to `services/api/` and this directory.

## Existing code to reuse

- **`src/clients/torrent/client.ts`** — every new method copies the shape already there:
  `new URL("<name>", await this.baseUrl())`, `HTTP_METHOD` from `@/types/http`, a
  `URLSearchParams` body, `this.normalizeHashes()` for the `|` join, and a JSDoc block whose second
  line is the wiki deep link. POST, like the existing `stop`/`remove`, even where the wiki says GET
  — that is what works against the running container.
- **`add()`'s `response.ok` check and its comment** (`client.ts:128`) — the model for NFR-6. Reuse
  the reasoning and the message shape; the new copy reads `TORRENT_CLIENT_REJECTED`.
- **`MoviesService.findOneFromDb` / `ShowsService.findOneFromDb`** — the ownership clause
  `where: { id, users: { some: { userId } } }`, and the rule that an unowned and a missing row are
  indistinguishable. `DownloadsService` writes the same clause locally rather than importing those
  services; see `../plan.md` § Approach for why, and do not introduce a shared helper.
- **`episodeDisplayTitle` / `seasonDisplayTitle`** — already duplicated in `movies/`, `episodes/`
  and `seasons/`. `Download.label` uses the same rendering (`<Show> S03E08`,
  `<Show> Temporada 3`). Follow the existing duplication; unifying it is a different change.
- **`ProcessJobsService.downloadRemove`** (`process-jobs.service.ts:260`) — the loser sweep goes
  inside it. Its `omitido: …` string and its return type stay exactly as they are, but its
  `!mediaSource.infoHash` early return **must no longer short-circuit the sweep**: under REQ-19 the
  winner can be a `LOCAL_FILE` upload, and sweeping only after `torrentClient.remove` means an
  upload winner leaves every losing torrent running forever with nothing to point at it
  (`../spec.md` NFR-5 (c)). Read the method before editing and restructure it so the sweep runs for
  a winner of either kind, with only the winner's own `remove` skipped.
- **`DownloadsService.handleTorrentCompleted`'s guard ladder** — REQ-13's new check is one more
  rung, placed **before** the existing `ERROR` rung. Keep the existing style: return a string,
  never throw, log with the `[torrentCompleted]` prefix. **The rung and the sibling pause both go in
  a shared method** that `UploadsService` also calls (REQ-19) — see `../plan.md` § Approach. Do not
  inline them here and copy them into the upload path.
- **`@CurrentUser()`** (`auth/decorators/current-user.decorator.ts`) and the
  `principal.type === 'user' ? principal.id : ''` idiom every resolver already uses.

## Steps

1. **Migration.** Edit `schema.prisma`: add `movieId Int?` + `movie Movie? @relation(...)` to
   `MediaSource` mirroring `episodeId`/`seasonId`; remove `mediaSourceId` and `mediaSource` from
   `Movie`. Run `bin/npm api run prisma:migrate`. Confirm both a modified `schema.prisma` and a new
   migration directory (Article III's check).
2. **Fix the compile fallout of step 1** before adding anything: `movies.service.ts` (lines 58, 72,
   291, 295, 360), `movies/entities/movies.entity.ts:37`, `movies/dto/create-movie.dto.ts:47`,
   `uploads.service.ts:212` and `:232`, `media-sources.service.ts:14-23`. The last one is the field
   the **worker** reads — `findOneFlat` must keep returning `movieId` with the same name and type;
   it just stops being derived.
3. **Torrent client.** `types.ts` first, then `client.ts`: the three new/changed methods (`add`,
   `info`, `start` — **not** `forceStart`), the 5.0 state sets (`stoppedDL`, `stoppedUP`,
   `forcedMetaDL` at minimum — `forcedDL`/`forcedMetaDL` must be *recognised* even though nothing
   here sets the flag), the `response.ok` checks, and an unrecognised state that no longer becomes
   `ERROR`.
4. **Tag building.** One small private helper per acquisition service, producing the tag list from
   the title (REQ-5's comma/whitespace sanitisation, with the id-derived fallback) and, for
   episodes and seasons, the English `Season <n>` / `Episode <n>` — unpadded. Pass it into
   `qbittorrent.add()`.
5. **Narrow the seven conflict guards.** Each is already a ternary on the target's status. Change
   the *condition* so the guard only fires for a `COMPLETED` target, and drop the
   `…_DOWNLOAD_IN_PROGRESS` half of the ternary — the film's becomes
   `movie.status === 'COMPLETED' && !input.force`, which also removes its dependence on the column
   step 1 dropped. Then delete the three now-unused keys from `error-keys.ts` and both
   `messages.{en,es}.ts`.
   **Do not touch `force`, the `@Args('force', …)`, the `…_ALREADY_COMPLETED` keys, the `updateMany`
   demote blocks, or anything in `upload-tickets.service.ts`** — all of that is
   `027-replace-completed-media` and removing it silently re-enables overwriting a finished film
   (`../plan.md` § Contract Freeze). Keep every cross-title `infoHash` collision check as it is.
   Two `.spec.ts` files assert the removed message (`episodes.service.spec.ts:152`,
   `seasons.service.spec.ts:143`) — update them to assert the guard no longer fires for a
   downloading target, rather than deleting the cases.
6. **`downloads/` surface.** `Download` entity, then the two queries (ownership clause → sibling
   `media_sources` by target → one `info(tag)` call → join on `infoHash` → ×100 on `progress`),
   then the three mutations. The list includes sources with **no** `infoHash`, which carry
   `kind: 'LOCAL_FILE'` and null live fields (REQ-18); the three mutations still refuse them with
   `DOWNLOAD_NOT_A_TORRENT` before any client call. A torrent absent from the client yields
   null live fields, never a dropped row.
7. **Race arbiter, as one shared method on `DownloadsService`.** Given a winning `mediaSourceId`:
   if any *other* source of the same target is already `READY` or `SCANNED`, report "ignored" and
   change nothing; otherwise stop every other non-terminal sibling in the torrent client and move it
   to `PAUSED`, leaving the winner running. Call it from `handleTorrentCompleted` after the
   self-idempotency rung and before the `ERROR` rung, keeping that method's return-a-string style.
8. **Wire the upload path into it (REQ-19).** In `uploads.service.ts`'s `onUploadFinish`, call the
   same method before moving the target to `ENCODING` and enqueuing `bull:process`; if it reports
   "ignored", finish the upload without touching the target's status and without enqueuing. Check
   `uploads.module.ts` for the import rather than assuming it is already there.
9. **Loser sweep.** In `downloadRemove`: select siblings by `movieId`/`episodeId`/`seasonId`,
   `remove(hashes, true)`, then `deleteMany` those rows. This must run whether or not the winner
   itself has an `infoHash` — see § Existing code to reuse.
10. **Tests** (below), then the typecheck and suite.

## Contract obligations

`api` is the producer of everything in `../spec.md` § GraphQL Contract Delta. Exactly that SDL must
appear in the regenerated `src/schema.gql` — Article VIII's check is a diff of the two.

Beyond the SDL:

- Every row in the spec's error table is an `ERROR_KEYS` constant with `extensions.i18n` (NFR-3).
  Only two keys are new — `DOWNLOAD_NOT_A_TORRENT` and `TORRENT_CLIENT_REJECTED` — and each needs an
  `en` and an `es` entry. The rest already exist in `src/i18n/` and must be reused, not retyped.
  **No user-facing literal at a raise site.**
- The three `…_DOWNLOAD_IN_PROGRESS` keys are **deleted** from `error-keys.ts` and both
  `messages.{en,es}.ts`. `web` deletes them from both JSON catalogs and from both components' key
  arrays in the same delivery — a key gone on one side only is invisible in both directions.
- The three `…_ALREADY_COMPLETED` keys and `force` are **untouched** (`027`). AC-23 re-exercises them.
- No `@AllowService()` on any of the five new operations.
- `downloadRemove` and `sourceScanned` keep their exact signatures. The worker is not in
  `services:`.

## Tests

Three units here can fail with no error anywhere, and all three are named in `spec.md` NFR-5. Each
file opens with a comment stating the failure class, per Article IX, and each case is written by
fault injection — verify it fails when the rule is removed.

- **`src/downloads/downloads.service.spec.ts`** (new) — defends against **a second source of the
  same target reaching `ENCODING`**. A `torrentCompleted` for a loser whose sibling is already
  `READY` must change nothing and enqueue nothing; remove the guard and the case must fail. Also
  covers that the winner is *not* stopped while its siblings are, and that a paused loser lands on
  `PAUSED` rather than `ERROR` — `ERROR` would be read by this very function as "superseded".
  Because the arbiter is one shared method, cover it here once and drive the upload entry point
  through it rather than writing a second near-identical suite.
- **`src/process-jobs/process-jobs.service.spec.ts`** (extend) — defends against **the sweep
  selecting siblings by tag rather than by target id**. A second title whose tag string collides
  must keep its downloads; switch the selection to a tag match and the case must fail. Also assert
  the winner's `deleteFiles: false` and the losers' `true` are not swapped. **And against an upload
  winner sweeping nothing** (NFR-5 (c)): `downloadRemove` for a `LOCAL_FILE` source whose target has
  two torrent siblings must still remove both with their files and delete both rows, while still
  answering `omitido: …`. Restore the `!infoHash` early return in front of the sweep and this case
  must fail — that is the whole point of it.

Not owed a test: the tag builder (a pure string function whose output is visible in qBittorrent and
covered by AC-1 to AC-3 — a bug here is loud, not silent), the new client methods (thin `fetch`
wrappers; their failure mode is the `response.ok` check, exercised live by AC-17), and the
`downloads` queries' ownership clause — that one is *not* silent, it returns a visible exception,
and `movies.service.spec.ts` already covers the identical clause it copies.
