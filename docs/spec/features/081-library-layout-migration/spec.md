# SPEC: Library Layout Migration (`spec.md`)

## Context & Goal

Since `072-plex-media-server` the worker names every file it files by a *layout* — `jellyfin`
(`Title (Year) [tmdbid=NNN]/Title (Year).mkv`) or `plex`
(`Title (Year) {tmdb-NNN}/Title (Year) {tmdb-NNN}.mkv`), built in
`services/worker/src/paths/build-output-path.ts` from the `libraryLayout` that
`services/api/src/process-jobs/process-jobs.service.ts` resolves per job out of the configured
`media_server_client`. That resolution happens at query time and is never snapshotted, which is
exactly right for a new encode and completely wrong for everything already on disk: an installation
that ran six months on Jellyfin and switches to Plex keeps a library full of `[tmdbid=]` folders that
Plex's scanner reads as release noise, falls back to matching by name and year, and gets wrong
anything with a homonym. The setting is reversible; its consequences are not. Today the only repair
is renaming a few hundred folders by hand.

The id is in the path, though, in the other layout's spelling — so the repair is mechanical. This
feature adds it, as three ordered steps an administrator starts once after changing media server:

1. **Remove the previous media server's own files** from inside each title folder — Jellyfin's
   `movie.nfo`, `folder.jpg`, `landscape.jpg`, `backdrop.jpg`, `logo.png`, `*.trickplay/`, and their
   per-episode equivalents. They are metadata for a server no longer in use, and they are removed
   *before* the rename so the migration never has to compute where a sidecar ended up.
2. **Rename the folders and files** Perceptor wrote, to the layout now configured.
3. **Trigger a full library scan** on the newly configured media server, so it indexes the new names
   rather than waiting for its own schedule and showing a half-empty library in the meantime.

Step 1 breaks Article XII as it stands — "Perceptor writes to the destinations root and never removes
from it" — so this feature carries a constitutional amendment, not a quiet exception. The amendment is
narrow: during a migration the user explicitly asked for, the worker may delete a file under the
destinations root **only** when it matches the enumerated list of the media server being migrated away
from. A video file is never deleted, by this feature or any other.

Step 3 needs nothing new: `refreshLibrary()` already exists on the `MediaServerClient` port
(`services/api/src/clients/media-server/types.ts`) and is already implemented by both clients —
`POST Library/Refresh` for Jellyfin, a refresh of every section for Plex. It is currently only reached
from the Settings screen's resync path; the migration becomes its second caller.

No pipeline stage in the root `CLAUDE.md` changes status. `buildOutputPath` stays the single authority
on what a name looks like, and the migration calls it rather than carrying a second, parallel
transformation that could drift from it. What changes is that the destination is no longer only decided
forward, at encode time, but can also be applied retroactively to what is already filed.

**One asymmetry worth stating up front, because it makes the two directions unequal.** Jellyfin writes
metadata into the library folder — that is why `services/worker/src/index.ts` sets `umask(0o002)` at
boot, so Jellyfin (same group, another uid) can write into each folder the worker creates. Plex does
not: it keeps metadata in its own data directory (`Plug-in Support/Databases/`, `Metadata/`), and the
local files it reads from a library folder are ones a *user* placed there for its Local Media Assets
agent. So step 1 has real work to do going `jellyfin` → `plex`, and **nothing** to do going
`plex` → `jellyfin`. The feature is symmetric in the renaming and deliberately asymmetric in the
deletion, because the filesystem is.

## Requirements

### Functional Requirements

- [ ] **REQ-1 (Migration plan)**: Must be able to report, without changing anything, how many titles
      on disk are filed under a layout other than the one now configured, and how many files and
      sidecars a migration would touch.
- [ ] **REQ-2 (Layout detected per title, never stored)**: Must determine a title's current layout
      from its recorded `filePath` rather than from a remembered previous setting — a path carrying
      `[tmdbid=<id>]` is `jellyfin`, one carrying `{tmdb-<id>}` is `plex`. A title whose path matches
      neither is reported as unrecognized and left untouched.
- [ ] **REQ-3 (Step 1 — remove the previous server's files)**: Must delete, before renaming anything,
      the files generated by the media server being migrated *away from*, matched against the list
      enumerated in "The sidecar lists" below. A file not on that list is never deleted.
- [ ] **REQ-4 (Deletion is depth-limited)**: Must look for those files only in a title's own folder
      and in its `Season NN/` subfolders — never recursively. A nested folder a user created (the
      real library has subtitle-release folders carrying their own `.nfo`) must be left alone
      entirely, contents included.
- [ ] **REQ-5 (Deletion matches whole names, not prefixes)**: Must match a per-episode sidecar by its
      exact suffix (`<video basename>.nfo`, `<video basename>-thumb.jpg`, `<video basename>.trickplay/`),
      never by a `<video basename>.*` glob — the real library has `<video basename>.spa.srt` subtitle
      files beside episodes that must survive.
- [ ] **REQ-6 (Never delete a video)**: Must never delete a video file, whatever list it appears to
      match — including a Plex `Plex Versions/` subfolder, which holds optimized *video*, not metadata.
- [ ] **REQ-7 (Step 2 — rename folders and files)**: Must rename, for every title filed under the
      other layout, both the title folder and the video file inside it to the names the configured
      layout produces, preserving the `Season NN/` structure for a series. The new name must be
      produced by the same authority that produced the old one (`buildOutputPath`), never by a string
      transformation of the old path.
- [ ] **REQ-8 (Database follows disk)**: Must update the stored `Movie.filePath` / `Episode.filePath`
      of every migrated title to the new path, and leave it unchanged for a title whose rename did not
      happen.
- [ ] **REQ-9 (Step 3 — full scan)**: Must trigger a full library scan on the configured media server
      once, after the renaming finishes, through the existing `refreshLibrary()` port. A failed or
      unreachable scan is logged and reported as an outcome — it must never fail the migration or
      undo it, the `notifyCreated` posture (a lost notification is repaired by a manual scan; a
      migration marked failed over it is not). With the media server set to `none` there is no scan
      and that is not an error.
- [ ] **REQ-10 (Offered only after a media-server change)**: Must offer the migration only when at
      least one title is filed under a layout other than the configured one. With the library already
      consistent the action is unavailable rather than a no-op the user can click. Switching the media
      server to `none` counts as a layout change, since `none` resolves to `jellyfin`.
- [ ] **REQ-11 (Explicit, never automatic)**: Must not start a migration as a side effect of saving a
      setting. Changing `media_server_client` saves the setting and makes the migration available; an
      administrator starts it.
- [ ] **REQ-12 (Skip, never overwrite)**: Must skip a title and record why, continuing with the rest,
      when its recorded file is missing from disk, when the destination name already exists, when its
      path is unrecognized (REQ-2), or when the rename fails. A skipped title's files and database row
      are left exactly as they were.
- [ ] **REQ-13 (Reportable outcome)**: Must report, when the migration finishes, how many titles were
      migrated, how many skipped, how many sidecars removed and whether the scan was triggered, and
      must name each skipped title with its reason.
- [ ] **REQ-14 (Administrator only)**: Must restrict the plan and the migration to an administrator,
      the `034` media-server-index precedent.

### Non-Functional & Operational Requirements

- [ ] **NFR-1 (Article XII amendment)**: The constitution must be amended before this feature is
      implemented — Article XII's prohibition is absolute as written and its **Check** enumerates every
      `rm`/`rmdir`/`unlink` under the destinations root as a violation. The amendment names this
      feature, confines the exception to the enumerated lists of REQ-3 during an explicitly requested
      migration, and restates that no video file is ever deleted. Run `/constitution` and land the
      amendment (1.3.0) before `/plan-feature`.
- [ ] **NFR-2 (`api` cannot write the library)**: `api` mounts the destinations root read-only
      (`docker-compose.yaml`, deliberately — the comment there says so). Every rename and delete must
      therefore happen in `worker`; `api` may enumerate and plan, owns the `filePath` columns
      (Article III), and owns step 3 since it is the only service that talks to a media server. No
      compose change: the two mounts this needs already exist.
- [ ] **NFR-3 (Paths stay behind the boundary)**: No absolute container path may appear in a GraphQL
      response (Article V). The plan and the outcome report counts and title names, never resolved
      paths; a skipped title is identified by its id and title, not by where its file is.
- [ ] **NFR-4 (Confined to the destinations root)**: Every rename and every delete must resolve inside
      the destinations root before touching disk, the same guard shape `047-source-deletion` uses to
      stay inside the downloads root. A path that escapes the root is a skip, not a best effort.
- [ ] **NFR-5 (Rename, never copy)**: A title folder must be moved with a rename, so its contents
      travel with it and nothing is duplicated or left behind. A rename that fails because source and
      destination are on different filesystems is a skip (REQ-12), never a fallback to copy-then-delete
      — a copy would double the library's size on disk and a delete afterwards is exactly what Article
      XII forbids. The destinations root is a single mount in practice (verified on the real library,
      one device under `Movies`, `Shows` and `Shorts`), so this is a guard, not an expected path.
- [ ] **NFR-6 (Interruptible and resumable)**: A migration interrupted mid-run (container restart) must
      leave the library in a state a second run completes rather than corrupts. This follows from REQ-2
      and REQ-8 together — a title is renamed and its row updated as one step, so a title already
      migrated is simply no longer a candidate — but it must be verified, not assumed.
- [ ] **NFR-7 (Not a download, not an encode)**: The migration must not occupy the encode queue or
      compete with an encode in flight. A rename is instant filesystem work; an encode is hours.
- [ ] **NFR-8 (No new dependency)**: Renaming and deleting are `node:fs` operations. Nothing is added
      to any `package.json`.

## GraphQL Contract Delta

```graphql
type LibraryLayoutMigrationPlan {
  """The layout now configured, and the one files will be renamed to."""
  targetLayout: String!
  """Titles whose recorded path is filed under another layout and would be renamed."""
  pendingTitles: Int!
  """Video files those titles would rename, across films and episodes."""
  pendingFiles: Int!
  """Files of the previous media server those titles would remove (step 1)."""
  pendingSidecars: Int!
  """Titles whose recorded path matches neither layout — reported, never migrated (REQ-2)."""
  unrecognizedTitles: Int!
}

type LibraryLayoutMigrationSkip {
  titleId: Int!
  title: String!
  """missing_file | destination_exists | unrecognized_path | outside_root | rename_failed"""
  reason: String!
}

type LibraryLayoutMigrationStatus {
  """never | running | done | failed"""
  state: String!
  targetLayout: String!
  titlesMigrated: Int!
  titlesSkipped: Int!
  filesRenamed: Int!
  sidecarsRemoved: Int!
  """not_requested | ok | failed — step 3's own outcome, never the run's (REQ-9)."""
  libraryScan: String!
  skipped: [LibraryLayoutMigrationSkip!]!
  startedAt: DateTime
  finishedAt: DateTime
}

type Query {
  libraryLayoutMigrationPlan: LibraryLayoutMigrationPlan!
  libraryLayoutMigrationStatus: LibraryLayoutMigrationStatus!
}

type Mutation {
  migrateLibraryLayout: LibraryLayoutMigrationStatus!
}
```

`state`, `reason` and `libraryScan` are plain `String!`, not GraphQL enums, for the reason the contract
document already records for `Movie.status`, `contentKind`, `compressionResolution` and
`MediaServerIndexStatus.state`: a value a consumer does not recognize yet must degrade, not fail to
parse. `targetLayout` is a layout name (`jellyfin`/`plex`), never a client id — `worker` knows naming
conventions, not media servers (`072`).

`migrateLibraryLayout` returns **immediately**, the `resyncMediaServerIndex` shape: it enqueues the work
and answers with the status as it stands at that moment. `web` polls `libraryLayoutMigrationStatus`
while `state` is `running`.

All three operations carry their own `@UseGuards(AdminGuard)` (REQ-14), the per-method
`ffprobe-logs.resolver.ts` precedent.

| Condition | HTTP / GraphQL error | Message the user sees |
| :-- | :-- | :-- |
| Caller is not an administrator | `ForbiddenException` | existing `error.auth.forbidden` copy |
| Nothing to migrate (`pendingTitles` is 0) | `BadRequestException` `error.libraryMigration.not_needed` | `La biblioteca ya está nombrada con el layout configurado.` |
| A migration is already running | `ConflictException` `error.libraryMigration.in_progress` | `Ya hay una migración en curso.` |
| The destinations root cannot be read | `ServiceUnavailableException` `error.libraryMigration.root_unavailable` | `No se puede leer la carpeta de la biblioteca.` |

A per-title failure is **not** an error: it is a `LibraryLayoutMigrationSkip` row with a `reason`
(REQ-12), and a failed step-3 scan is `libraryScan: "failed"` (REQ-9) — both the `069-title-refresh`
posture, an outcome the user reads rather than an exception that abandons the run. `web` translates each
`reason` through its own catalog; an unknown `reason` renders the raw string rather than breaking the
list.

What each consumer does with the errors:

- **`web`** — the Settings → media-server tab renders the migration block only when `pendingTitles > 0`
  (REQ-10). `not_needed` and `in_progress` are both treated as "re-read the status and render it"
  rather than as failures to show the user, since both mean the button should not have been clickable;
  `root_unavailable` and `forbidden` surface as a toast. A finished run with
  `libraryScan: "failed"` renders a notice pointing at the media server's own scan, not an error.
- **`worker`** — consumes no GraphQL error here; it reports its outcome back, and its own reporting must
  tolerate being received more than once, the `encodeCompleted`/`encodeFailed` durability posture of
  `038-encode-report-durability`. `[NEEDS CLARIFICATION: does the worker report the migration outcome
  through a new mutation, or write progress to Redis the way the media-server index does and let api's
  status query read it? The second adds no GraphQL surface and no retry obligation, which Article X
  favours, but it is the first time worker would write api-owned state outside a mutation — and step 3
  is api's, so api has to learn the run finished either way.]`

### Queue payload delta

A second, parallel contract the GraphQL schema does not cover — declared in both
`services/api/src/queue/types.ts` and `services/worker/src/queue/types.ts`, changed together:

```
queue: bull:library-layout     (a queue of its own, not a job name on bull:process or bull:encode — NFR-7)
job:   migrate-layout
payload: {
  targetLayout: 'jellyfin' | 'plex',
  removeFilesOf: 'jellyfin' | 'plex',    // the server being migrated away from (step 1)
  destinationsRoot: string,              // resolved absolute container path, api-owned (Article V)
  titles: Array<{
    titleId: number,                     // Movie.id or Episode.id
    kind: 'MOVIE' | 'EPISODE',
    currentPath: string,                 // absolute container path, as recorded
    ...the catalog fields buildOutputPath needs, or a precomputed targetPath
  }>
}
```

`[NEEDS CLARIFICATION: who builds targetPath? buildOutputPath lives in worker
(services/worker/src/paths/), and REQ-7 requires the migration use it rather than a second
implementation — which argues the worker builds it and the payload carries only the title's catalog
fields. But api needs the same names to answer pendingFiles in the plan (REQ-1) without the worker.
Either api duplicates the naming rules (the drift risk REQ-7 exists to prevent) or the plan's counts are
computed by detecting layout only (REQ-2), never by building target names. Decide which.]`

## The sidecar lists (REQ-3, REQ-4, REQ-5)

Deleted only when migrating **away from** that media server, only at the two depths REQ-4 allows, and
never when the file is a video (REQ-6).

from documentation — this is what Jellyfin has actually written there. Counts are occurrences found.

### Plex

**Empty — nothing is deleted when migrating away from Plex.** Plex keeps its metadata in its own data
directory (`Plug-in Support/Databases/com.plexapp.plugins.library.db`, `Metadata/`), not in the library
folder. The local files Plex *reads* from a library folder — `poster.jpg`, `fanart.jpg` and friends, via
its Local Media Assets agent — are ones a user placed there deliberately, so deleting them would be
destroying user data, not cleaning up after a server. `.plexmatch` is likewise user-authored, a manual
match hint. And `Plex Versions/` holds optimized *video* (REQ-6).

This asymmetry is the design, not an omission: step 1 is where `jellyfin` → `plex` does its work, and
`plex` → `jellyfin` goes straight to step 2.

## Out of Scope

- **A `none` layout.** A third layout writing no id marker was considered and rejected on 2026-10-02:
  it is the only transition that destroys information, since the id is never written to disk and the
  repair cannot be mechanical. The whole point of this feature is that `jellyfin` ↔ `plex` *is*
  mechanical.
- **Adopting files Perceptor did not record.** A video sitting in the library with no
  `Movie.filePath`/`Episode.filePath` pointing at it is invisible to this migration. Finding and
  claiming orphans is a different feature (it needs matching by name against the catalog, which is what
  `069-title-refresh`'s media-server reconciliation already does from the other side).
- **Rewriting sidecar *contents*.** A `.nfo` is deleted, never edited. Translating Jellyfin metadata
  into something Plex reads is a metadata-management feature; Perceptor's position is that the media
  server owns its own metadata.
- **Rebuilding the local media-server index.** Step 3 is a scan on the *media server*, which is a
  different thing from `034`'s own index of it. Conflating them hides which one failed; `034`'s
  "Re-sincronizar" button already exists for the other half.
- **Deleting an emptied old folder.** NFR-5 renames rather than copies, so a stale empty directory
  should never arise. If one somehow does, it stays — removing a directory under the destinations root is
  exactly what Article XII's **Check** names, and NFR-1's amendment is narrowed to the enumerated *file*
  lists.
- **A dry-run that lists every title.** The plan reports counts (REQ-1), not a per-title preview. A
  preview is a bigger `web` surface, and the skip report (REQ-13) already names whatever went wrong
  after the fact.
