# PLAN: Show Refresh Sweep — `api` (`api/plan.md`)

## Scope

`api` is the only service in this feature. It adds one nullable column to `Show`, persists TMDB's
series status into it from the three code paths that already hold a `ShowDetail`, extracts the
catalog half of `ShowsService.refresh()` so it has exactly one implementation, and replaces the
`RefreshShowsTask` stub with a real sweep that selects series due under a status-dependent cadence
and refreshes them.

It is explicitly **not** doing: any GraphQL change (the `schema.gql` diff must be empty), any
media-server reconciliation from the sweep (REQ-8 — that stays in `refresh()`, which the task does
not call), any `web` or `worker` change, and any edit to `scheduler.registry.ts`, whose
`refresh_shows` definition and `mediaType: 'show'` gating are already correct.

Writes are confined to `services/api/` and this directory. Anything else is a stop-and-report.

**Before starting**, check the working tree: `073-automatic-episode-acquisition` is being implemented
concurrently and owns `scheduler.module.ts`'s imports/providers arrays and a new
`scheduler.registry.ts` entry. Rebase onto its work; do not revert it.

## Existing code to reuse

- `services/api/src/shows/shows.service.ts:369` — the inner `try` of `refresh()`. This **is** the
  per-series work of the sweep: `tmdb.details()`, the `show.update()` of
  `title`/`overview`/`posterUrl`/`releaseDate`/`originalLanguage`, `syncSeasonsAndEpisodes()`, the
  `seasonsSyncedAt` stamp, and the `cacheShows()` Redis catalog-cache replacement. Extract it verbatim
  into a private method (suggested `syncCatalogFromTmdb(showId, tmdbId)`) that keeps throwing on
  failure; `refresh()` then calls it inside the `try/catch` it already has, so its
  `RefreshCatalogOutcome.DONE`/`FAILED` behaviour is unchanged.
- `services/api/src/shows/shows.service.ts:237` — `syncSeasonsAndEpisodes()`. Already does REQ-5 and
  REQ-6: sequential per season, upserts, season 0 included, `undefined` rather than `null` on an
  absent date so an empty TMDB field never blanks a stored value. Do not touch it.
- `services/api/src/shows/shows.service.ts:228` — `hydrateClaimKey()` and
  `HYDRATE_CLAIM_TTL_SECONDS`. The one key every writer of a series' catalog serialises on. The
  sweep's public entry point (suggested `syncCatalogClaimed(showId, tmdbId): Promise<boolean>`) takes
  it with `SET … EX … NX` exactly as `hydrate()` does, returns `false` untouched when it is held, and
  deletes it in a `finally`. `refresh()` keeps taking the claim itself, at its current place and with
  its current `ConflictException` — do not move it into the shared body, because the two callers want
  different things when the claim is lost.
- `services/api/src/clients/tmdb/client.ts:81` — the `SHOW` mapper already puts TMDB's status on
  `ShowDetail.status`. No client change is needed; it is only ever dropped today.
- `services/api/src/scheduler/tasks/refresh-episodes.task.ts` — the shape to copy for the new handler:
  module-level constants for the windows, one `findMany` for selection, an early `return
  { itemsProcessed: 0 }` when nothing is due (NFR-2), a sequential loop with a per-item `try/catch`,
  and a final `throw` naming failed/total/written counts so `runTask` records `FAILED`.
- `services/api/src/scheduler/tasks/refresh-episodes.task.spec.ts` — the suite shape and the Article
  IX header style to follow.

## Steps

1. **Schema.** Add `tmdbStatus String?` to `model Show` in `prisma/schema.prisma`, placed next to
   `seasonsSyncedAt`. Generate with `bin/npm api run prisma:migrate`, migration name
   `add_show_tmdb_status`. No backfill (`../plan.md` § Migrations). Do not name it `status`:
   `Show.status` is already `MediaStatus` and means `MISSING`/`COMPLETED`.

2. **Persist the status.** In `ShowsService`, write `tmdbStatus: detail.status` on the `show.update()`
   inside the catalog step, so `refresh()` and the sweep both fill it. `hydrate()` does not update
   the show row today — add `tmdbStatus` to the `show.update()` it already makes for
   `seasonsSyncedAt`, or let it call the extracted step; either way a freshly registered series has
   the column filled once hydration finishes. `register()`'s `show.create()` builds from a cached
   `MediaSearchResult`, which carries no status — leave it out there and let hydration fill it
   seconds later (REQ-1 expects exactly this).

3. **Extract the catalog step.** Pull the body described in § Existing code to reuse into
   `syncCatalogFromTmdb()`. Behaviour-preserving: the `seasonsSyncedAt` stamp stays **after** the
   season loop (REQ-10), the method keeps throwing rather than returning an outcome, and the
   media-server call stays in `refresh()` outside it (REQ-8). Then add the claimed public entry
   point for the task.

4. **The sweep.** Replace `RefreshShowsTask.run()`. It injects `PrismaService` and `ShowsService`.

   - Two module-level constants: `ENDED_REFRESH_DAYS = 180`, `CONTINUING_REFRESH_DAYS = 30`, plus
     `const ENDED_STATUSES = ['Ended', 'Canceled']`. Constants, not Settings (REQ-13).
   - Selection, one `findMany` over `show`, `select: { id: true, tmdbId: true }`, ordered by
     `seasonsSyncedAt: 'asc'` with nulls first so a run is deterministic:

     ```
     OR: [
       { seasonsSyncedAt: null },
       { tmdbStatus: { in: ENDED_STATUSES }, seasonsSyncedAt: { lt: endedCutoff } },
       {
         OR: [{ tmdbStatus: null }, { tmdbStatus: { notIn: ENDED_STATUSES } }],
         seasonsSyncedAt: { lt: continuingCutoff },
       },
     ]
     ```

     **The `{ tmdbStatus: null }` arm is load-bearing and must not be simplified away.** `notIn`
     becomes SQL `NOT IN`, which evaluates to `NULL` — not `TRUE` — for a `NULL` column, so without
     it every series that predates the migration is silently skipped forever. See `../plan.md`
     § Risks, row 1.
   - Empty selection → `return { itemsProcessed: 0 }` before any TMDB call (NFR-2).
   - Loop sequentially (NFR-1). Per series: `await shows.syncCatalogClaimed(id, tmdbId)` in a
     `try/catch`. `false` (claim held) → skip, uncounted, not a failure. Resolved → `written += 1`.
     Threw → `failed += 1`, continue.
   - `failed > 0` → `throw new Error('refresh_shows: N of M series failed; K refreshed successfully')`.
     Otherwise `return { itemsProcessed: written }` (REQ-11, REQ-12).

5. **Module wiring.** Add `ShowsModule` to `SchedulerModule`'s `imports`, no `forwardRef` (see
   `../plan.md` § Approach — `073` has already put `IndexerModule`, which imports `ShowsModule`, in
   the same array). Boot the stack and confirm `api` goes healthy before trusting any test run.

6. **Docs.** Update the two `services/api/CLAUDE.md` passages named in § Files. The root `CLAUDE.md`
   is the orchestrator's, not this slice's — leave it.

## Tests

- `src/scheduler/tasks/refresh-shows.task.spec.ts` (**new**, owed). Every failure this defends against
  is silent: the sweep reports `SUCCESS` with a plausible count while doing the wrong thing, and
  nothing else in the system notices a series that stopped being refreshed. Open with the Article IX
  header naming that class. Cases, each written to fail if the rule it pins is removed:
  - a series with `tmdbStatus: NULL` and a sync older than the continuing window is selected — assert
    against the generated `where`, so dropping the `{ tmdbStatus: null }` arm fails the case;
  - both cadence boundaries, both sides: `Ended` at 100 days not selected / at 200 selected,
    `Returning Series` at 20 not selected / at 40 selected;
  - `seasonsSyncedAt: null` selected regardless of age;
  - an unrecognised status (`In Production`, and a value TMDB does not have today) takes the
    continuing window, never the ended one;
  - nothing due → zero calls into `ShowsService`;
  - series two is still refreshed when series one throws, and the handler then throws with both
    counts in the message;
  - a series whose claim is held (entry point resolves `false`) is neither counted nor treated as a
    failure.
- `src/shows/shows.service.spec.ts` (modified, owed for the new surface only): `tmdbStatus` is written
  from `detail.status`; the claimed entry point returns `false` and issues no TMDB call when the
  Redis `SET NX` does not return `'OK'`; a rejecting `seasonDetails` leaves the `seasonsSyncedAt`
  stamp unwritten. The **existing** `refresh` cases are the regression guard for step 3 and must pass
  unmodified — if one needs editing, the extraction changed behaviour and that is a stop-and-report.
- Not owed: the migration (Article III's `git status` check covers it), and the `SchedulerModule`
  import (a bad module graph fails at boot, loudly, which § Verification's health check catches).
