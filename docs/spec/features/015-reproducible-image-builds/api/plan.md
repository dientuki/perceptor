# PLAN: Reproducible Image Builds — `api` (`api/plan.md`)

## Scope

One thing: make the Nest application bootable from an image that contains no `src/` directory.

`app.module.ts:31` passes `autoSchemaFile: join(process.cwd(), 'src/schema.gql')`. In the `dev`
container that path exists because `/app` is the bind-mounted working copy. In the `runner` image it
does not — that stage copies `dist`, `prisma`, `node_modules` and `package*.json` and nothing else —
so the first thing a production `api` does is try to write a generated file into a directory that
was never created. Today nobody sees it, because `bin/prod` mounts the source over the image
(`../spec.md` § 4).

Explicitly **not** this slice: the `Dockerfile` and its `npm prune` smoke check (`../infra/plan.md`),
the `.dockerignore` that keeps `services/api/.env` out of the image (`../infra/plan.md`), the
hardcoded DSN in `prisma.service.ts` and the `url`-less `datasource` (both listed in `../spec.md`
§ *Out of Scope* — leave them exactly as they are), and Prisma migrations on boot (also out of
scope).

Writes are confined to `services/api/` and this directory.

## Existing code to reuse

- `services/api/src/app.module.ts` — the `GraphQLModule.forRoot` options block already there. Change
  the value of `autoSchemaFile`, not the module wiring, and keep the `join(process.cwd(), …)`
  expression for the non-production branch so the dev artifact lands exactly where it does today.
- `services/api/src/auth/auth.constants.ts` — the repo's existing example of reading an environment
  variable at module load and deciding boot behaviour from it. Follow its shape (read once, decide
  once); do not introduce a config service for one boolean.

Article IV is the constraint that makes the in-memory branch the right answer rather than "copy
`src/schema.gql` into the image": the schema is **generated at boot from decorators**, never
authored and never shipped. A production container regenerating it in memory is that article
working as intended. `services/api/src/schema.gql` stays checked in and stays regenerated by every
dev boot — a diff on it during this feature is expected only if a decorator changed, which here it
must not.

## Steps

1. In `app.module.ts`, make `autoSchemaFile` conditional on `process.env.NODE_ENV === 'production'`:
   `true` (in-memory) when it is, the current `join(process.cwd(), 'src/schema.gql')` when it is
   not. Add a short English comment naming the reason — the `runner` image has no `src/`.
2. Confirm nothing else in the module reads or writes a path under `src/` at runtime
   (`grep -rn "process.cwd()" services/api/src`). Today `app.module.ts:31` is the only hit; if a
   second appears, report it — it is the same bug in another place.
3. Typecheck and run the suite. The count must not move.

## Contract obligations

None. `../spec.md` § *GraphQL Contract Delta* is **None**, and this change must not alter the
schema by so much as a field description: the same decorators produce the same SDL whether it is
written to disk or held in memory. If `bin/npm api test` or the running dev container produce a
`schema.gql` diff, stop — that is a contract change nobody approved (Article VIII).

## Tests

**None owed.** The failure this change prevents is not silent: without it a production container
crashes at boot, and with it the container answers `/graphql` — which is exactly what the compose
healthcheck already probes (`docker-compose.yaml`, `api.healthcheck`). A unit test around
`process.env.NODE_ENV` in a module definition would assert that an `if` is an `if`; Article IX's
standard (`media-roots.service.spec.ts`, `magnet.spec.ts`) is for logic whose bug produces a wrong
*result*, not a dead container.

The real check is AC-7: `api` reaches `healthy` under `bin/prod`.
