# PLAN: Movie Refresh Sweep — `api` (`api/plan.md`)

## Scope

This service owns the whole feature: the migration, the TMDB client change, the closure rule, the two
write paths that fill the new columns, and the `refresh_movies` handler body. No other service is
involved — there is no GraphQL delta, so `web` and `worker` have nothing to consume and nothing to
retype (`../spec.md` NFR-7).

Explicitly **not** doing, even though the code is right there: exposing any of the five new columns
through GraphQL, touching a film's `MISSING`/`COMPLETED` status or `filePath`, touching `isShort` or
`contentKind`, rebuilding the media-server index, and anything that searches the indexer or attaches a
source. That last one is a different task id in a different spec (`acquire_movies`).

Writes are confined to `services/api/` and this directory. Anything else is a stop-and-report.

## Existing code to reuse

- `services/api/src/clients/tmdb/client.ts` — `earliestMovieReleaseDate()` is the method being
  replaced, and its body is the loop to keep: it already walks `data.results[].release_dates[]`,
  slices each `release_date` to ten characters and validates it with a `^\d{4}-\d{2}-\d{2}$` regex
  before comparing as strings. Keep all of that; only the accumulation changes from one `earliest` to
  four. `fetchOne()` is the request helper; do not add a second one.
- `services/api/src/movies/movies.service.ts` — `refreshCatalog(id, tmdbId)` (currently `private`,
  around line 340) is the single definition of what a catalog refresh writes. Extend it; do not write
  a second update path for the sweep. `topUpCatalogFacts()` is where the release-dates call already
  happens on a cold registration, behind its `needsRelease` guard — the typed dates ride that exact
  branch. `cacheMovies()`/`getCachedMovie()` carry the Redis entry the new optional fields travel on.
  `refresh()` (the `069` public entry) needs no change: it already calls `refreshCatalog`, so REQ-11
  arrives for free.
- `services/api/src/media/content-kind.ts` + `content-kind.spec.ts` (`057`) — the precedent for a pure
  classification rule in its own file with its own spec. `release-window.ts` follows this shape, not
  the inline `isShortRuntime` helper in `movies.service.ts`.
- `services/api/src/scheduler/tasks/refresh-episodes.task.ts` (`041`) — the handler shape to copy:
  a module-level constant for the window (not a Setting), an early return of
  `{ itemsProcessed: 0 }` when nothing is selected so an idle installation makes zero external calls,
  a strictly sequential loop with a per-item `try`/`catch`, and a final `throw` naming the
  failed/total/succeeded counts. Its spec file is the model for the new one, including the
  Article IX header paragraph.
- `services/api/src/scheduler/scheduler.service.ts` — `runTask` already turns a handler throw into a
  `FAILED` run row with the error string and records `itemsProcessed` on success. The task does not
  create run rows, does not catch its own final throw, and does not check `movies_enabled` — the
  registry's existing `mediaType: 'movie'` and `runTask`'s `isAvailable` guard do that (REQ-16).
- `services/api/src/scheduler/scheduler.registry.ts` — the `refresh_movies` entry, its
  `defaultCron: '0 4 * * *'` and its `mediaType: 'movie'` already exist and are correct. Do not touch
  this file. The `schedule_refresh_movies_enabled`/`_cron` rows already exist in
  `prisma/seeds/settings.ts` (off by default) — do not touch that either.

## Steps

1. **Schema.** Add to `model Movie` in `prisma/schema.prisma`: `theatricalReleaseDate DateTime?`,
   `digitalReleaseDate DateTime?`, `physicalReleaseDate DateTime?`, `tmdbStatus String?`,
   `catalogClosedAt DateTime?`. Generate the migration with
   `bin/npm api run prisma:migrate` — never hand-write the SQL (Article III). `tmdbStatus`, not
   `status`: `Movie.status` is `MediaStatus` and means something entirely different.
2. **Client result shape.** In `clients/types.ts`, add `MovieReleaseDates` with four
   `string | null` day fields (`earliest`, `theatrical`, `digital`, `physical`, each `YYYY-MM-DD` or
   `null`) and change the `MovieDBClient` interface accordingly. Days stay strings here; the `Date`
   conversion belongs where the row is written, as it does today.
3. **Client.** In `clients/tmdb/client.ts`, replace `earliestMovieReleaseDate()` with the method that
   returns `MovieReleaseDates` from the same single `GET movie/{id}/release_dates` request. Keep the
   existing validation and string comparison. TMDB's release types, as a module-level constant beside
   the method with the endpoint's doc URL above it (Article XI's first exception): `2` and `3` both
   feed `theatrical` (limited and wide), `4` feeds `digital`, `5` feeds `physical`. `1` (premiere) and
   `6` (TV) feed no typed field but, like every other entry, still count toward `earliest` — which is
   what keeps REQ-2 true. An entry with a missing or unrecognised type still counts toward `earliest`
   and nothing else.
4. **Closure rule.** New `movies/release-window.ts`, exporting one pure function that takes the four
   days (or `Date`s — pick one and keep it), the `tmdbStatus` and a `now`, and answers whether the
   film is closed. The rule, from `../spec.md` REQ-8: closed when `tmdbStatus === 'Canceled'`; closed
   when no date is in the future **and** the newest known date is more than 365 days before `now`;
   open when any date is in the future; open when no date is known at all and the status is not
   `Canceled`. The 365 is a module-level constant, not a Setting. Compare on UTC day boundaries, the
   way `refresh-episodes.task.ts` builds its cutoff — a film released exactly 365 days ago must land
   on one side of the line deliberately, not by accident of the clock.
5. **The write path.** In `movies.service.ts`:
   - `refreshCatalog` becomes public (the sweep calls it; `refresh()` still calls it internally) and,
     inside its existing `try`, writes the three typed dates and `tmdbStatus` alongside the fields it
     already writes, then evaluates step 4's rule against the values it just read and writes
     `catalogClosedAt` — a timestamp when closed, `null` when open. Both directions on every
     successful refresh: that single write is REQ-8 and REQ-11 at once. Nothing moves into the
     `catch` — a failed refresh leaves `catalogClosedAt` exactly as it was (REQ-9), which the existing
     shape already gives you as long as the evaluation stays inside the `try`.
   - Keep the existing "never erase" posture: an absent value passes `undefined` to Prisma, not
     `null`. `catalogClosedAt` is the one exception — it is this feature's own column and must be
     settable back to `null`.
   - `topUpCatalogFacts`'s `needsRelease` branch now stores all four days on the cache entry, and the
     `needsDetails` branch additionally carries TMDB's production status. Add a **new, distinctly
     named** optional field to the cached `MediaSearchResult` for that status —
     `MediaSearchResult.status` is already taken and already means the pipeline status on the wire
     (`media/entities/media-search-result.entity.ts`). Writing TMDB's string into it would render a
     bogus badge in `web` with no error anywhere.
   - `register()` writes the three typed dates and the status from the topped-up entry when present,
     and leaves them `undefined` when not. It must gain **no** TMDB request: a warm-cache registration
     makes the same number of calls it makes today (REQ-5/REQ-3). It never writes `catalogClosedAt` —
     see § Decisions below.
   - Retarget both former `earliestMovieReleaseDate` call sites (around lines 351 and 523) at the new
     method; `releaseDate` keeps being derived exactly as it is today, from `earliest` falling back to
     the detail's own `release_date`.
6. **The sweep.** Replace `RefreshMoviesTask.run()`'s body. Inject `PrismaService` and `MoviesService`.
   Select `{ status: { not: COMPLETED }, catalogClosedAt: null }`, taking `id` and `tmdbId` only;
   return `{ itemsProcessed: 0 }` immediately on an empty selection (NFR-2). Loop sequentially —
   never `Promise.all` (NFR-1) — calling `refreshCatalog(id, tmdbId)` per film, counting the `DONE`
   results and the `FAILED` ones. `refreshCatalog` reports failure by return value rather than
   throwing, so the per-item `try`/`catch` of `041` is belt-and-braces here, not the primary
   mechanism: count a `FAILED` return the same as a caught throw. Return the success count when
   nothing failed; otherwise `throw` an error naming failed / total / succeeded, which is what makes
   `runTask` record `FAILED` (REQ-14, REQ-15).
7. **Module wiring.** Add `MoviesModule` to `SchedulerModule`'s imports. Boot the stack and read the
   log: if Nest reports a circular dependency or hands the task an `undefined` `MoviesService`, wrap
   it as `forwardRef(() => MoviesModule)` — `settings.module.ts` has the pattern and the comment
   explaining why. `MoviesModule` already exports `MoviesService`; `TmdbClient` is already reachable
   through the `SettingsModule` the scheduler imports, which is how `RefreshEpisodesTask` gets it.
8. **Docs.** Update the "Register title in DB" row of the root `CLAUDE.md` pipeline table and the
   `scheduler/` and `movies/` notes in `services/api/CLAUDE.md`: `refresh_movies` is no longer a stub,
   and a film now carries typed release dates, a TMDB production status and a closure marker. Say
   plainly that the sweep never acquires anything.

## Contract obligations

`../spec.md` § GraphQL Contract Delta says **None**, and it is frozen. Concretely, this slice owes the
other services *nothing new*, and owes them one thing it must not do: **no `@Field()` on any of the
five new columns**, and no change to `TitleRefresh` or `RefreshCatalogOutcome`. A film that closed or
reopened during a manual refresh still reports `DONE`.

`schema.gql` must not appear in the final diff. No decorator changes, so there is nothing for the
code-first generator to regenerate.

If the delta looks wrong from in here — for instance if you conclude the detail page really should
show the digital date — stop and report. Do not add the field.

## Tests

Owed under Article IX, because the failure is silent:

- `services/api/src/movies/release-window.spec.ts` — **the** test of this feature. A wrong closure
  rule produces no error, no log and no UI: a film simply stops being refreshed forever, and the
  digital release that did eventually arrive is never seen. Cover both sides of the 365-day boundary,
  a future date with old dates beside it (open), `Canceled` with a future date (closed), every date
  `null` with a non-`Canceled` status (open, never closed by age), and "newest date wins" when the
  four dates disagree. Open with the Article IX header paragraph naming that failure.
- `services/api/src/scheduler/tasks/refresh-movies.task.spec.ts` — three silent failures of its own:
  a selection that includes `COMPLETED` or closed films silently spends the TMDB budget this feature
  exists to protect (and REQ-10 is unverifiable from outside); a `Promise.all` instead of a sequential
  loop rate-limits a shared key and leaves the sweep half-done with no error; and a run that counts a
  `FAILED` refresh as processed, or swallows the final throw, reports a clean `SUCCESS` on a sweep
  that did nothing. Also assert the empty-selection early return makes zero client calls (NFR-2).
  Mock `PrismaService` and `MoviesService` the way `refresh-episodes.task.spec.ts` mocks its two.
- `services/api/src/clients/tmdb/client.spec.ts` — extend, do not replace. The existing cases for
  `earliestMovieReleaseDate` become cases for the new method and must keep proving `earliest` is
  unchanged (REQ-2 — a regression here silently moves every film in `062`'s calendar). Add: type `2`
  and type `3` both landing in `theatrical`, earliest-across-countries per type, a type with no entry
  anywhere staying `null`, and an unrecognised or missing type counting toward `earliest` only.
- `services/api/src/movies/movies.service.spec.ts` — extend the existing registration assertions to
  pin the call budget (a warm-cache registration must not gain a request) and add one case proving a
  failed `refreshCatalog` leaves `catalogClosedAt` untouched. That second one is REQ-9, whose live
  check (AC-11) needs an invalid TMDB key and so will not be run often.

Not owed: the module wiring (a bad import fails loudly at boot, and the manual trigger in
`../plan.md` § Verification exercises it), and the migration itself (`migrate status` and AC-13 cover
it).

## Decisions this plan makes that the spec did not

- **`register()` never closes a film.** A film registered today whose dates are all three years old is
  closable on its face, but REQ-8 ties closure to a successful *refresh*, and registration is not one.
  The film is created open and the first sweep closes it. One rule, one place, one code path.
- **The sweep counts a `FAILED` return exactly like a thrown error.** `refreshCatalog` already reports
  a TMDB failure by returning `RefreshCatalogOutcome.FAILED` rather than throwing (it catches and
  logs), so a loop that only counted throws would report every failed film as a success. REQ-14's
  counts mean "films whose refresh did not complete", by either mechanism.
- **Days stay `YYYY-MM-DD` strings across the client boundary** and become `Date`s only where the row
  is written, matching what `earliestMovieReleaseDate` does today. Moving the conversion into the
  client would be a wider change than this feature needs.
