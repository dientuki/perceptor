# PLAN: Installable PWA (LAN-scoped) (`plan.md`)

## Approach

One service, one slice: everything lands in `services/web`. `api` and `worker` are untouched, and
so is `docker-compose*.yaml` — nothing here needs a new container, port, volume or environment
variable, because the secure context the feature depends on already exists as `USE_HTTPS`
(`066-https-local-ca`) and `web` already receives the fact through `EnvironmentInfo.useHttps`.

The shape is four pieces plus one guard.

**The manifest** stays a static file at `services/web/src/app/manifest.json`, extended in place with
`id`, `start_url`, `scope`, `description`, `lang` and `purpose: any` icons beside the two maskable
ones already declared. It is not converted to `app/manifest.ts`: nothing in it is computed, and a
generator function that returns a constant is a layer Article X does not allow us to add.

**The `<head>` tags** move out of the literal `<head>` block in `src/app/layout.tsx` and into Next's
`metadata`/`viewport` exports on the same file — `applicationName` replaces the hand-written
`application-name` meta, `appleWebApp: { capable, title, statusBarStyle }` replaces the hand-written
`apple-mobile-web-app-title` and covers REQ-7, and `viewport.themeColor` carries the light/dark pair.
The icon links themselves are already generated by Next from `src/app/icon0.svg`, `icon1.png` and
`apple-icon.png`; nothing is added there.

**The service worker** is a hand-written `services/web/public/sw.js`, served at `/sw.js` with the
root scope, registered from a small client component mounted in the root layout beside the existing
`ThemeProvider`/`SidebarProvider`. No `next-pwa`, no `workbox` (NFR-1). Its whole policy is: pass
every request through to the network untouched; on a **navigation** request that rejects, answer with
a cached copy of `/offline`; cache nothing else, ever (REQ-3). The `fetch` handler exists both to
serve that fallback and because Chromium will not offer installation to a site whose worker has
none. `install` calls `skipWaiting()`, `activate` calls `clients.claim()` and deletes every cache
whose name is not the current version's — so a new image's worker takes over open tabs immediately
and cannot leave an older cache behind (REQ-8).

**The offline document** is a Next route at `src/app/offline/page.tsx`, rendered and translated
through the existing next-intl catalogs like any other screen. Two constraints shape it and an
implementer must not "fix" them: it is served from the cache at a moment when **no other network
request can succeed**, so its CSS chunk, its fonts and its JS bundle are all unavailable. It
therefore carries its own inline `<style>` element rather than relying on Tailwind's stylesheet, and
its retry control is an `<a href="">` — an empty href resolves to the current URL, which is the
destination that failed, so the retry works with zero JavaScript on the page.

**The guard** is `src/proxy.ts`. Its matcher already exempts `_next/static`, `favicon.ico` and image
extensions, but not `/sw.js`, `/manifest.json` or `/offline`, and none of the three is in
`PUBLIC_ROUTES` — so today each one answers a `307` to `/login` for a request with no cookie. A
manifest is fetched without credentials by default, which means this would break installability for
*every* user, signed in or not, with no error anywhere except a line in DevTools nobody reads. All
three go into `PUBLIC_ROUTES`. This is the single most important line of the feature.

**Settings → Environment** (REQ-6) gains one row inside the existing `EnvironmentPanel.tsx`, which is
already a `"use client"` component: it combines `environment.useHttps` with a client-side
`window.isSecureContext` check made in an effect, and renders the existing `Badge` next to the
existing HTTPS badge and `/ca.crt` link rather than growing a new panel.

## Order of Work

One service, so the ordering is internal. The only hard edge is that the proxy exemption must land
before any live verification, or every check fails for the wrong reason.

| Step | Service | Why it must come here |
| :-- | :-- | :-- |
| 1 | `web` | `proxy.ts` `PUBLIC_ROUTES` — until `/sw.js`, `/manifest.json` and `/offline` stop redirecting to `/login`, nothing downstream can be observed working |
| 2 | `web` | `/offline` route + its catalog entries — the worker precaches it, so it must exist first |
| 3 | `web` | `public/sw.js` and the registration component in `layout.tsx` |
| 4 | `web` | manifest fields + the `metadata`/`viewport` exports (independent of 2–3; can run in parallel with them) |
| 5 | `web` | `EnvironmentPanel` installability row + `en`/`es` keys |
| 6 | `web` | `services/web/CLAUDE.md` — the cache policy and the NFR-4 staleness note (see Contract Freeze) |

Steps 2–3 are one chain. Step 4 and step 5 are independent of that chain and of each other.

## Contract Freeze

`spec.md` § GraphQL Contract Delta is **None**, and that is the frozen part: this feature adds no
GraphQL field, no query, no argument and no error key of its own. `EnvironmentInfo.useHttps` is
consumed exactly as `066` shipped it. An implementer who finds themselves wanting a server field for
"is this installation installable" has taken a wrong turn — the answer depends on the *browser's*
secure context, which no server can observe.

Three things will look wrong from inside the slice and must not be changed:

- **Caching nothing.** A precache of the build's static assets is the obvious "improvement" and is
  exactly what REQ-3 forbids; it is how a self-hosted installation serves yesterday's interface after
  `docker compose pull && up -d`. The only cache entry is `/offline`.
- **The offline page's inline `<style>` and `<a href="">`.** Both look like a regression next to
  every other screen in this service. Both are load-bearing: the document renders when no stylesheet
  and no script can be fetched.
- **NFR-4's note.** The spec asks for the staleness bound to be written down "where the worker
  lives". Article XI forbids that as a code comment, so it is written down here and in
  `services/web/CLAUDE.md` instead, and `public/sw.js` carries no comment.

## Migrations

None. No Prisma model, no seed, no `.env` variable, no compose change.

## Risks

| Risk | How it fails | Mitigation |
| :-- | :-- | :-- |
| `/sw.js` or `/manifest.json` caught by `proxy.ts` | A `307` to `/login` where a script or JSON was expected. Registration throws in an effect nobody watches; the browser simply never offers to install. No log, no user-visible error | Step 1 comes first; AC-1 (DevTools reports no manifest error) and AC-2 (exactly one activated worker) both fail loudly if this regresses |
| A stale worker keeps serving an old build | The user updates the image, reloads, and sees the old interface — the single failure this feature exists to avoid | REQ-3's pass-through policy plus `skipWaiting`/`clients.claim`; AC-6 checks that Cache Storage holds nothing but the offline document |
| The worker intercepts a tus upload | A resumable `PATCH /uploads` buffered or retried by the worker corrupts a multi-gigabyte upload, and the failure surfaces far from here | The `fetch` handler returns without calling `respondWith` for anything that is not a failed navigation; AC-7 watches the Network panel for a `(ServiceWorker)` attribution |
| The offline document renders unstyled or dead | It is only ever seen when nothing else can load, so the defect is invisible in every normal test | Inline `<style>`, no-JS retry; AC-4 exercises it with the stack actually stopped |
| Registration attempted over plain HTTP | A console error on every page load in the common LAN-by-IP deployment, and a support question that costs more than the feature | Guard on `window.isSecureContext && "serviceWorker" in navigator` before registering; AC-3 requires a clean console on `http://` |
| A worker registered by a past install outlives the feature | It keeps controlling clients after the code that installed it is gone | Cache-name versioning with an activate-time sweep; a `/sw.js` that stops existing fails the browser's own update check, which unregisters it |

## Verification

```bash
bin/cli web npx --no tsc --noEmit
bin/cli web node scripts/check-messages.mjs
bin/npm web run lint
git diff --stat services/api services/worker
```

`bin/npm web run build` is **not** run against a live dev stack — it clobbers `.next` and un-hydrates
every page. Run it only with the dev stack down, or let the release image build cover it.

Manual pass, on a stack with `USE_TRAEFIK=true` and `USE_HTTPS=true`, from a device that trusts
`certs/ca.crt`:

1. Load the app over `https://${DOMAIN}`. DevTools → Application → Manifest: no installability
   error; Service Workers: one activated worker, scope `/` (AC-1, AC-2).
2. Install it. The window opens standalone, with the icon, no address bar (AC-1).
3. `docker compose stop web api`, then navigate inside the installed window: the Perceptor offline
   screen, styled, in the active locale, with a working retry once the stack is back (AC-4). From its
   console, `fetch('/graphql')` must reject rather than resolve with the offline document (AC-5).
4. Application → Cache Storage holds the offline document and nothing else; change a string in
   `messages/en.json`, restart `web`, reload — the new string is there on the first reload (AC-6).
5. Import a large file through the import modal; Network shows the `PATCH /uploads` requests with no
   `(ServiceWorker)` attribution (AC-7).
6. Reach the same stack at `http://<lan-ip>:${WEB_PORT}`: no worker registered, clean console,
   everything else identical (AC-3).
7. Settings → Environment shows the installability row both ways — flip `USE_HTTPS` off and recreate
   `web` to see the unavailable branch naming HTTPS (AC-9).
8. iOS Safari → Add to Home Screen, launch from the icon (AC-8).
